01 · Visión general

Resumen ejecutivo y alcance

SIGEC Cloud es una aplicación web de gestión de consultorio médico. Centraliza expediente clínico, agenda, caja/pagos e información administrativa mediante una SPA en React conectada directamente a Supabase.

Aplicación webReact 18, Vite 5, React Router 6 y CSS propio; renderizado de cliente.
Servicios gestionadosSupabase Auth, PostgreSQL, Row Level Security, Realtime y Edge Functions.
Perfiles operativosRoles almacenados en el perfil: médico y secretaria.
Despliegue webNetlify sirve los artefactos estáticos de Vite con fallback SPA.

Alcance implementado

  • Inicio/cierre de sesión, carga de perfil, protección básica de rutas y estado activo de cuenta.
  • Dashboard con resumen diario de citas, sala de espera y recaudación; accesos a pacientes, agenda, pagos y configuración.
  • Pacientes y expediente individual con información general, secciones clínicas, evoluciones, informes médicos imprimibles y plantillas de plan/tratamiento.
  • Agenda/citas con estados, paciente registrado o texto libre, métodos de pago y registro de cobros.
  • Pagos con consulta de registros e informe contable por período para el perfil médico.
  • Configuración de tasa BCV y administración de usuarios/accesos para el médico.
Límite importante: este documento describe lo encontrado en el código fuente y migraciones del repositorio. No certifica cumplimiento normativo, calidad clínica, disponibilidad, configuración real del proyecto Supabase ni políticas del proveedor. Antes de usarlo con datos reales debe completarse una revisión de seguridad y privacidad.

Convenciones de precisión

Implementado comportamiento visible en código o SQL. Observación diferencia o limitación comprobada. Recomendación mejora propuesta no asumida como existente.

04 · Navegación y sesión

Rutas y autenticación

RutaVistaProtección de frontend

Ciclo de autenticación

  1. AuthProvider consulta la sesión persistida con supabase.auth.getSession().
  2. Si existe identidad, consulta el registro profiles por su UUID y determina rol.
  3. Suscribe onAuthStateChange para sincronizar el usuario tras login/logout/refresco.
  4. Las rutas muestran carga inicial; después permiten el árbol privado si user existe.
  5. Cuando lee is_active=false, limpia el perfil/usuario y difiere signOut().
Observación: el guard de ruta comprueba solo la identidad, no que exista un perfil válido o un rol reconocido. El acceso efectivo a la base depende de RLS; la interfaz no es por sí sola una frontera de seguridad.

05 · Funcionalidad

Módulos del sistema

Dashboard

Consulta citas del día ordenadas por hora y pagos del día. Calcula total de citas, pacientes con estado “En sala de espera” y suma de pagos en USD. La acción “Atender” cambia el estado a “Completada” y registra la marca temporal. La cifra recaudada se muestra al médico. El día de consulta se calcula en el navegador con fecha ISO UTC.

Pacientes y expedientes

Permite alta de paciente, listado alfabético, búsqueda en memoria por nombre/cédula/historia y navegación a detalle. Historia es asignada por trigger al insertar. El detalle organiza información general, examen funcional, examen físico, evoluciones, informes y diagnóstico/tratamiento. El expediente clínico se guarda en columnas JSONB para secciones variables. Ofrece impresión de receta/informe; el texto insertado se escapa antes de construir el HTML imprimible.

Agenda

Registra cita para un paciente seleccionado o un nombre escrito libremente. Conserva algunos datos de contacto duplicados en la cita. Permite revisar todas las citas, cambiar estatus, iniciar pago y alternar a la tabla de pagos. Estados: Pendiente, En sala de espera, Confirmada, Completada, Cancelada, No asistió. Método de pago de cita admite Pendiente de Pago, Pago Móvil, Zelle, Efectivo USD, Efectivo Bs, Transferencia y Exonerado.

Pagos y caja

Permite asociar un cobro opcionalmente a paciente, método, monto, fecha, descripción y referencia. Los métodos son Pago Móvil, Zelle, Efectivo USD, Efectivo Bs, Transferencia y Exonerado. Para Exonerado se guarda monto cero. La vista de consulta lista movimientos; el médico puede filtrar por fechas, ver totales/agrupación por método e imprimir un informe contable.

Configuración

Consulta la fila única de configuración con ID 1. La interfaz modifica la tasa BCV; otros metadatos del consultorio están en el esquema, pero no se actualizan en el formulario observado. El panel médico permite crear usuarios con rol, y habilitar/inhabilitar cuentas conservando el historial.

Plantillas e informes médicos

Desde el expediente, el médico puede guardar plantillas reutilizables de plan/tratamiento y crear informes médicos con fecha y texto libre. La impresión incorpora identidad textual de la clínica y datos del paciente. No se encontró almacenamiento de archivos adjuntos ni firma electrónica.

07 · Seguridad

Autorización, RLS y límites actuales

El cliente usa la URL de Supabase y la clave anon expuestas como variables Vite, lo cual es normal solo si RLS está correctamente configurado. El token de sesión identifica al usuario. Las Edge Functions usan SUPABASE_SERVICE_ROLE_KEY, que nunca debe estar en el bundle web.

Matriz observada

RecursoLecturaEscritura / borrado según RLS
profilesAutenticado: su propio perfil o todos si cuenta activa.No se define política de escritura de cliente en estas migraciones; altas/accesos por función admin.
configuracionSolo usuario autenticado y activo.UPDATE únicamente médico activo; no se ve política INSERT/DELETE.
pacientesTodo usuario autenticado activo tiene política FOR ALL (CRUD completo); el alcance no restringe por rol.
citasTodo usuario autenticado activo tiene política FOR ALL (CRUD completo); el alcance no restringe por rol.
evolucionesTodo usuario autenticado activo tiene política FOR ALL (CRUD completo); el alcance no restringe por rol.
pagosUsuarios activos autenticados pueden leer.INSERT y UPDATE permitidos; no hay política DELETE en las migraciones revisadas.
plantillasUsuarios activos autenticados.Crear/actualizar/borrar solo médico activo.
informes_medicosUsuarios activos autenticados.Crear/actualizar solo médico activo; no se define DELETE.
Hallazgo de riesgo alto: que una acción esté oculta en la interfaz no la vuelve segura. Por ejemplo, el borrado de pacientes está condicionado por rol médico en el componente, pero la política RLS de pacientes permite FOR ALL a cualquier usuario autenticado activo; de manera similar, la actualización general del expediente y los cambios de cita no quedan limitados a médico por RLS. Revisar la autorización a nivel de base antes de producción.

Controles implementados

  • Las rutas del cliente requieren una sesión Supabase.
  • La aplicación cancela una sesión cuando detecta profiles.is_active=false.
  • La función SQL is_active_user() es SECURITY DEFINER con search_path=public y RLS desactivado dentro de la función; retorna falso si no encuentra perfil activo.
  • Las políticas actualizadas para recursos protegen operaciones con identidad autenticada y perfil activo.
  • El médico activo es verificado dentro de Edge Functions antes de administrar cuentas y dentro de RLS para config/plantillas/informes.
  • Al inhabilitar, se actualiza perfil y se banea la identidad Auth; se intenta restaurar el perfil si falla el ban. No se permite inhabilitarse uno mismo ni inhabilitar al último médico activo.

Controles pendientes recomendados

  1. Definir permisos CRUD explícitos por rol y por tabla; separar lectura, alta, actualización y borrado.
  2. Evaluar separar datos identificativos de datos clínicos y restringir lectura de evoluciones/informes al médico.
  3. Asegurar que cada fila nueva/actualizada mantiene coherencia entre paciente, cita y perfil de autor.
  4. Validar perfil activo/rol en guard de aplicación, pero mantener RLS como autoridad final.
  5. Revisar CORS de funciones (actualmente origen comodín) y limitarlo a dominios de producción si el flujo lo permite.
  6. Definir política de contraseñas, recuperación, rotación, MFA para cuentas médicas y proceso de baja/alta documentado.
  7. Establecer clasificación de datos, retención, copias cifradas, auditoría de accesos y respuesta ante incidentes.
Claves: VITE_SUPABASE_ANON_KEY es una clave pública pensada para cliente y no reemplaza RLS. SUPABASE_SERVICE_ROLE_KEY omite controles normales de RLS y debe guardarse solo en secrets de Supabase Functions/servidor.

Posible discrepancia: el cliente escucha cambios en pagos, informes y plantillas, pero la migración de publicación no los agrega. La entrega Realtime no sustituye una consulta inicial: las vistas primero cargan datos y luego se suscriben. El dashboard actualiza su agregación al recibir eventos de citas/pagos solo si la publicación los entrega.

09 · Backend privilegiado

Supabase Edge Functions

Las funciones están escritas en TypeScript para Deno y comparten cabeceras CORS desde _shared/cors.ts. Ambas atienden preflight OPTIONS y devuelven JSON.

create-user

  1. Requiere encabezado Authorization.
  2. Usa URL y service role desde secretos de entorno; verifica la sesión con auth.getUser.
  3. Busca rol actual en profiles y exige médico.
  4. Valida email, contraseña, nombre y rol (contraseña mínima de seis caracteres).
  5. Crea usuario Auth con email ya confirmado y luego inserta perfil.
  6. Si falla el perfil intenta borrar la identidad creada; devuelve identificador/nombre/rol al éxito.

manage-user-access

Exige médico activo, valida usuario objetivo y booleano active; impide auto-inhabilitación y bloquear al último médico activo. Marca perfil/fecha/actor y aplica baneo Auth de larga duración al inhabilitar. Si el baneo falla intenta revertir el perfil. La habilitación limpia metadatos de baja y elimina el ban.

Recomendación: añadir límites de tasa/abuso, validación de esquemas de request, registro de auditoría sin secretos ni datos clínicos, pruebas de autorización de cada ruta y restricciones CORS por dominio. Definir explícitamente el comportamiento esperado de errores parciales.

Impresión

La aplicación compone documentos HTML para receta, informe médico e informe contable y llama window.print(). Los estilos @media print definen páginas Carta. El usuario puede elegir impresora o “Guardar como PDF” en el diálogo del navegador. No es un servicio de PDF firmado/archivado.

Fuera del alcance visto

  • No hay dependencia para envío de correo, SMS, WhatsApp ni recordatorios automáticos.
  • No se encontró almacenamiento de documentos en Supabase Storage.
  • No se observa integración de pago en línea, firma digital o interoperabilidad médica externa.
  • No hay servidor de aplicación propio; las operaciones cliente se canalizan mediante Supabase y las dos funciones administrativas.

12 · Operación de negocio

Flujos funcionales principales

Alta y atención del paciente

  1. Usuario con sesión registra nombre y datos demográficos básicos.
  2. PostgreSQL asigna UUID e historia clínica correlativa desde una secuencia.
  3. El expediente se abre por identificador; el médico completa secciones clínicas.
  4. Una evolución referencia al paciente y al perfil que la crea; signos vitales se guardan en JSONB.
  5. El médico puede crear informe, usar plantilla y producir impresión local.

Ciclo de cita y cobro

  1. La secretaria o médico registra una cita para paciente existente o captura nombre libre.
  2. Se almacena fecha, hora, motivo, estatus inicial y datos de cobro previstos.
  3. El estado cambia desde Agenda o el dashboard; “Atender” en el dashboard marca completada.
  4. Se registra un pago como movimiento separado, con referencia opcional a cita y paciente.
  5. El médico genera informe de ingresos de un intervalo y puede imprimirlo.
Distinción contable: citas.monto_usd es el monto planificado/relacionado con la cita; pagos.monto es el ingreso registrado. El dashboard suma pagos, no los montos de citas.

Ciclo de acceso de usuarios

  1. Médico activo crea cuenta y perfil desde Configuración mediante función protegida.
  2. El colaborador inicia sesión con credenciales asignadas.
  3. El médico puede inhabilitar la cuenta desde la lista; se conserva la fila de perfil e historial de negocio, pero se banea Auth.
  4. Al reactivar, se elimina el ban y el perfil se marca activo.

El código crea la identidad con email confirmado y contraseña temporal suministrada. El flujo de cambio obligatorio de contraseña inicial no se observa implementado.

Roadmap propuesto

  1. Seguridad y privacidad: RLS mínimo privilegio, MFA médico, ciclo de cuenta, auditoría y revisión de tratamiento de datos.
  2. Fiabilidad: pruebas de políticas/funciones, validación de esquema, manejo de errores uniforme, CI y ambiente staging.
  3. Integridad clínica/financiera: constraints/relaciones consistentes, timestamps, zona horaria y reglas explícitas de anulación.
  4. Escalabilidad: paginación, índices basados en consultas, observabilidad y procedimiento de respaldos/restauración.
  5. Usabilidad: accesibilidad, estados vacíos, formularios validados, confirmación para acciones destructivas y responsive testado.

14 · Mantenimiento

Operación y continuidad

Responsabilidades operativas recomendadas

  • Administrador Supabase: secretos, políticas, migraciones, funciones, usuarios privilegiados, límites/cuotas y copias.
  • Responsable clínico: roles de la clínica, exactitud de catálogo y uso clínico; no comparte credenciales.
  • Responsable de aplicación: releases de frontend, observabilidad, revisión de dependencias y recuperación de fallos.

Lista previa a producción

  • Aplicar migrations 001–008 en entorno objetivo y revisar errores de ejecución.
  • Probar políticas RLS con rol médico, secretaria, usuario desactivado y sesión sin perfil.
  • Confirmar Realtime habilitado para las tablas requeridas.
  • Validar alta/cierre de cuentas y recuperación/rotación de contraseña.
  • Ejecutar build de producción y revisar rutas directas y actualización del navegador.
  • Probar exportación a papel/PDF de informe médico, receta e informe contable.
  • Definir política de respaldo, retención y prueba de restauración.
  • Verificar que no se publique .env ni SERVICE_ROLE_KEY y que las variables VITE apunten al proyecto correcto.
  • Documentar contacto y procedimiento ante incidente o indisponibilidad.

Supuestos de continuidad

La disponibilidad de Auth, base, funciones, canales realtime y almacenamiento del sistema depende del proyecto/proveedor Supabase y su región. La disponibilidad Netlify cubre el frontend estático, no garantiza la base de datos. El repositorio no demuestra una política de backup, SLA, RPO/RTO, monitorización o plan de desastre; deben determinarse fuera del código y comprobarse periódicamente.
